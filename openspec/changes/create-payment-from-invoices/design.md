## Context

目前付款與發票已分別存在，付款分配資料可表達一筆付款對應一張或多張發票；付款資料也已有客戶關聯與銀行帳戶欄位。新流程需要在同一個交易中完成查驗、付款建立、分配、發票餘額更新及銀行入帳。

## Goals / Non-Goals

**Goals:**

- 新增由單筆或多筆發票建立單筆付款的 API 與頁面操作。
- 保證所選發票的客戶及幣別一致，並自動帶入付款人與金額。
- 支援全額及部分付款，建立後立即入帳。
- 保留原有手動付款入口。

**Non-Goals:**

- 不改變原有手動付款的資料流程。
- 不允許跨客戶、跨幣別或無發票餘額的合併付款。
- 不新增獨立的 Payment-to-Invoice 直接欄位；關聯沿用付款分配資料。

## Decisions

- **以發票選取結果建立單一付款命令：** 新增專用請求／回應模型及 API，避免改變既有手動付款 API 的相容性。
- **使用付款分配資料建立關聯：** 一張發票建立一筆分配，多張發票建立多筆分配；付款金額低於總餘額時按穩定順序分配，讓部分付款結果可預期。
- **在服務交易邊界完成全部異動：** 先驗證並鎖定發票，再建立付款、分配、發票狀態及銀行收入交易；任一驗證或寫入失敗即回滾。
- **付款人以客戶 ID 為主、名稱作快照：** Payment 的 `customer_id` 關聯所選發票客戶，`payer_name` 同時保存建立當下顯示名稱。
- **關聯付款強制銀行帳戶：** 由發票建立的付款直接建立為已入帳，銀行帳戶必須屬於目前組織、啟用且幣別一致；原有手動付款仍可依原規則待入帳。
- **前端先做可用性篩選、後端重新驗證：** 前端只顯示同客戶／同幣別的可選發票，後端仍以組織範圍與交易鎖定作為最終安全邊界。

## Risks / Trade-offs

- [部分付款的分配順序會影響各發票剩餘餘額] → 使用固定的發票日期／ID 順序，並在回應中回傳每筆分配結果。
- [並行操作可能同時選取同一發票] → 建立付款時鎖定發票並在鎖定後重新檢查狀態與餘額。
- [客戶名稱日後變更] → `customer_id` 作為正式關聯，`payer_name` 僅作付款建立時的名稱快照。

## Migration Plan

沿用現有付款、發票、付款分配及銀行交易資料表，不需資料移轉；部署後新增 API 與 UI。若需回滾，只移除新入口與服務，不影響既有手動付款資料。
